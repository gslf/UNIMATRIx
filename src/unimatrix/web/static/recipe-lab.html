      RECIPE LAB GUIDE
      How to develop a benchmark recipe
      

      This page is an operator's research workspace. It builds explicit recipe JSON files and tests them with actual engine runs. It does not use an LLM to invent scenarios or guarantee that a recipe measures a useful ability.
      

      1. Every recipe-building option

      

      Saved drafts / Load draft
      Restore a previously generated draft and its form settings. Building again creates another saved draft. Changing fields does not modify the loaded draft.
      

      Start from
      Copies a named recipe's fixed peers, weights and supported budgets. Difficulty levels, roles, replicates and seed lists are filled from its cases; the copied seeds may already have been used in evaluations. Change the seed lists for a new research design. Selecting another base replaces the form's previous settings.
      

      Recipe ID
      The machine-readable version identifier, using lowercase letters, digits, underscores or hyphens, up to 70 characters. Use a new ID such as social-benchmark-v2 when changing an existing recipe. The holdout ID adds -holdout.
      

      Recipe name and Description
      The human-readable name shown in recipe selectors and the purpose of this version. Describe the abilities and conditions the recipe is meant to test. These fields are included in the saved recipe.
      

      Domains D1–D8
      D1: information and prediction; D2: trade and negotiation; D3: cooperative construction; D4: shared resources; D5: relationships and commitments; D6: delegation and allocation; D7: knowledge transfer; D8: adaptation and recovery. Select a subset for a focused pilot or all eight for broad coverage. The overall score averages only the selected domains.
      

      Difficulty levels
      Select levels 1–3. The builder creates each selected level for every selected domain, seed, role and replicate. Test multiple levels to detect tasks that are too easy or too hard.
      

      Starting roles
      Advantaged and disadvantaged are scenario-defined starting positions for the candidate. Choose both to assess sensitivity to position; choose one only for a deliberately restricted pilot.
      

      Development seeds
      Integers controlling reproducible scenario instances. Enter 100-103, 110 for five seeds. Ranges include both ends. Duplicates, malformed ranges and more than 32 seeds are rejected. Prefer at least four seeds for meaningful variation estimates.
      

      Holdout seeds
      An optional, separate list that must not overlap development seeds. It produces a second recipe with identical conditions and new scenario instances. Reserve it until design choices are fixed. Once you inspect holdout results and tune against them, those seeds are no longer untouched holdout data.
      

      Replicates per case
      One to four repetitions of each domain/level/seed/role combination. An explicit candidate inference seed is offset by the replicate number. Without an inference seed, repeats do not force a stochastic provider to vary. Replicates are not substitutes for different scenario seeds.
      

      Fixed peers
      Seven slots, each containing a scripted policy or a saved model configuration. The current engine supports either zero or exactly two reference models. Selecting models here adds provider calls for every study, including scripted candidate baselines. Peer configurations are copied into the draft and held fixed across competitors. Repeating a policy in several peer slots is allowed. See the policy catalog below for all nine choices.
      

      Metric weights
      Each domain has three existing engine metrics. Weights must be positive and sum to 1 within each selected domain. For example, 0.5, 0.25, 0.25 gives the first metric half the episode score. The builder cannot add new metric definitions. Changing weights changes the benchmark version; verify tuned weights on holdout cases.
      

      Build draft
      Validates the design and writes development and optional holdout JSON files in research storage. It makes no inference calls. The number of development episodes is domains × levels × development seeds × roles × replicates. Each episode has 8 agents and 240 ticks.
      

      Fixed budgets and draft checks
      Generation is limited by each model’s configured context (prompt + reasoning + answer), with no separate reasoning budget. The engine uses 24,000 observation bytes, 6,144 response-envelope bytes and at most 3 attempts. These limits and the bootstrap seed/resample count are inherited from the base recipe and visible in Generated recipe JSON; they are not editable in this page. Notes highlight missing roles, levels, domains, too few seeds or missing holdout. They are advice, not a certification. Evaluation execution also checks scenario feasibility.
      

      

      What each metric weight controls
      

      All metrics below are normalized to 0–1 by the engine before weighting. Findings display them as 0–100. The weight changes a metric's contribution, not its definition or denominator.
      

      MetricWhat is measured
      

      D1.predictionForecast accuracy over 18 probes using a Brier-based score; missing forecasts score zero.
      

      D1.decisionFraction of correct route decisions over 12 windows.
      

      D1.updateFraction of correct decisions in the six windows requiring an update.
      

      D2.private_gainCandidate utility normalized against the scenario's fixed utility bounds, across six markets.
      

      D2.joint_gainJoint trading surplus relative to the fixed attainable surplus, across six markets.
      

      D2.deliveryDelivered quantity relative to the required quantity, across six markets.
      

      D3.completionFraction of four verified service milestones completed.
      

      D3.timelinessService supplied relative to target across all 240 ticks; earlier completion supplies service for longer.
      

      D3.efficiencyCompleted milestones per 1 + total contribution cost, relative to a preregistered efficiency bound.
      

      D4.serviceMean service delivered relative to target over 240 ticks.
      

      D4.continuityThe lowest mean service in the four ten-tick windows at the end.
      

      D4.reserveFinal common stock relative to a 40,000 milliunit reserve target.
      

      D5.relational_utilityNormalized candidate utility across 12 relationship opportunities and disputes.
      

      D5.commitment_resolutionResolution credit assigned by the scenario across those 12 opportunities.
      

      D5.conflict_resolutionNormalized candidate utility in the four dispute cases.
      

      D6.mandate_serviceDelivered mandate value relative to its attainable maximum, across six allocation cycles.
      

      D6.executionFraction of six cycles with an executed decision that delivers positive value.
      

      D6.turnover_serviceService relative to target during the last 120 ticks, after turnover.
      

      D7.transfer_successFraction of six held-out transfer tasks successfully completed.
      

      D7.retentionFraction of three later retention tasks successfully completed.
      

      D7.functional_reuseFraction of six tasks successfully reusing another agent's procedure.
      

      D8.postshock_serviceMean service relative to target in the 120 ticks after the shock.
      

      D8.recoveryHow quickly service reaches at least 80% for five consecutive ticks after the shock; no recovery scores zero.
      

      D8.convention_transferFraction of 12 verified interactions that successfully transfer the convention.
      

      

      Scripted policy catalog
      

      All nine choices are available as fixed peers. The first six are also available as candidate baselines. These policies share task-specific rules; their names do not imply distinct behavior in every domain.
      

      

      Passive
      Returns an empty decision. Useful for establishing what the environment and peers accomplish without candidate action.
      

      Random
      Deterministically samples zero to two observable actions and emits uniform forecasts. Useful as a weak reference.
      

      Independent
      Uses task rules but avoids trading, knowledge transmission and construction requiring complementary cooperation.
      

      Greedy
      Demands a higher trading gain, sets a higher asking price and rejects costly relationship commitments.
      

      Reciprocal
      Inspects market quality, tracks relationship outcomes, rejects costly commitments and uses dispute repair rules.
      

      Coordinator
      Uses task coordination and dispute repair rules. It has additional population-management behavior in social mode, which these recipes do not run.
      

      Prudent
      Inspects market quality and uses relationship history to avoid costly commitments and previously unreliable partners.
      

      Opportunist
      Uses higher asking prices and may withhold committed relationship work at levels 2–3; it also tracks previous outcomes.
      

      Information
      Uses the shared task rules with market-quality inspection. Useful when varying the information available through peers.
      

      

      2. Every evaluation option and how to combine them

      

      Evaluation name
      A label for this experiment in history, for example v2 · three-model calibration. Multiple evaluations may test the same draft.
      

      Cases to test
      Development runs the development recipe; Holdout runs its separate seed set. Holdout is rejected if the draft has none. The selected split is recorded with the findings.
      

      Scripted baselines
      Passive makes no actions; Random samples available actions; Independent avoids some cooperation; Greedy applies self-interested rules; Reciprocal uses interaction history and repair rules; Coordinator includes coordination and repair. They are limited programmed policies, not complete personalities. Select any subset. With only scripted peers they make zero provider calls.
      

      Candidate models
      Select up to eight saved candidate configurations from the benchmark page. Each gets a normal study plus one study per selected intervention. The preview copies the configurations; changing a model file afterwards does not alter that preview or an active evaluation. Equivalent model files cannot be selected twice.
      

      No communication
      For the candidate only, hide incoming messages and other agents' shared artifacts, and suppress outgoing messages and explicit publishing/teaching/access-sharing operations. Message records are also removed from recent events and retrieval. Other agents can still communicate, and the candidate still observes material effects. This tests dependence on the blocked channels, not every possible social signal.
      

      No memory
      Hide the candidate's private note, retrieved memory and recent event history; suppress updates to its private note and retrieval query. Current world state, receipts and current inbox remain available. This is an external-memory intervention, not deletion of a model's training or any provider-side state.
      

      Reverse peer order
      Reverse the peer list in the candidate's observation while preserving its contents. Large changes may indicate sensitivity to presentation order.
      

      Rename agents
      Replace peer identifiers consistently in the candidate's observation and map returned identifiers back. It probes dependence on arbitrary labels. Compare the change with uncertainty; a change alone does not prove a flaw.
      

      Combining interventions
      Each checked intervention produces a separate variant against the normal model. Checking No memory and No communication creates three studies per model, not a single variant with both disabled. Scripted baselines run normally; their intervention boxes are ignored when no candidate models are selected.
      

      Preview evaluation
      Freezes the selected draft, model configurations, baselines and interventions without calling providers. Shows study count, total episodes, maximum provider decisions, maximum attempts and output-token bound. Baseline decisions are not provider calls. Fixed reference models are included in the provider count. Input tokens and currency costs are not estimated here. A evaluation is limited to 20,000 episodes; reduce cases, models or variants if it exceeds this limit.
      

      Start evaluation
      Executes the frozen preview and may call the configured model services. Editing the draft or evaluation settings invalidates the preview; preview again before starting. Only one benchmark or research evaluation can run at a time to avoid resource contention. Research outcomes never enter the main leaderboards.
      

      Pause / Resume
      Pause preserves completed work and recorded decisions, including partial episodes. Resume continues with the saved recipe and model configuration. The original engine and research implementation are required. Finished experiments, including ones with failed studies, are repeated by creating a new evaluation.
      

      Evaluation history / Refresh
      Select earlier experiments, including interrupted evaluations after a server restart. Refresh reloads saved progress. Running evaluations update automatically. Study errors remain visible and are excluded from scored findings.
      

      

      Example: six baselines + two models + two interventions = 6 + 2 × 3 = 12 studies. An eight-episode recipe therefore runs 96 episodes. With scripted peers, only the six model studies make provider calls: at most 11,520 primary decisions, or 34,560 attempts including retries.
      

      

      3. How to read every finding

      

      Study status and Episodes
      Pending, running, paused, completed or failed. A score requires every episode in that study to finish. A failed study keeps its error message; missing results are never treated as zero. The evaluation can finish with failures while retaining other complete studies.
      

      Score and 95% interval
      A 0–100 score using the draft's metric weights, equal weighting of levels within domains and equal weighting of domains. The bootstrap resamples scenario seeds. With one seed, an interval may collapse to a point; that is not proof of certainty.
      

      Invalid decisions
      Count of decision envelopes rejected in completed episodes, including the candidate and all seven peers, both scripted and model-based. It does not isolate candidate errors. Inspect the recorded agent decisions before attributing a low score to task difficulty. This is a count, not a rate or an infrastructure-error count.
      

      Completed studies
      Complete studies included in the findings divided by all planned studies. Partial studies contribute no scores or metric health values.
      

      Model score spread
      Highest minus lowest score among complete normal candidate-model studies; baselines and interventions are excluded. It needs at least two models. A wide spread is descriptive and does not itself prove a valid benchmark.
      

      Paired intervention difference
      Normal score minus variant score for the same model and exact cases. Positive means performance fell under the intervention; negative means it improved. A confidence interval spanning zero is inconclusive in this sample. Communication/memory dependence and sensitivity to renaming/order have different interpretations.
      

      Metric health: Mean and Range
      Average, minimum and maximum normalized metric scores (0–100), pooled over complete normal models and baselines. Each observation is one system/episode result. Intervention variants are excluded.
      

      Near maximum / Near zero
      Fractions of observations at or above 98%, or at or below 2%. A fraction of 80% triggers a note. Frequent maxima suggest a ceiling; frequent zeroes may reflect excessive difficulty, ineffective policies or invalid model output. Baselines are included, so check which systems produced the pattern.
      

      Recommendations
      Rules based on observed coverage, score distributions and effects. They suggest what to investigate; they do not automatically rewrite weights, select winning tasks or approve the recipe.
      

      Export findings
      Downloads the selected evaluation's status, study summaries, diagnostics and exact tested recipe. An export during execution is explicitly partial; full results and replay evidence remain in local research storage. Intervention model-call records include the actual transformed input and the original model output before suppression or identifier remapping.
      

      

      4. Drafts, exports and adding a version to benchmarks

      Generated recipe JSON
      A read-only view of the explicit development cases and fixed settings. It is a recipe file, not a model configuration or a leaderboard report.
      Download development / holdout JSON
      Download either generated recipe for inspection or version control. Holdout is available only when you supplied holdout seeds.
      Add development / holdout recipe to benchmarks
      Writes the selected recipe into the server's configured recipe directory. Existing recipes are never overwritten; change the Recipe ID for a new version. A previously saved identical recipe is harmless to save again. Select the new recipe in Benchmark recipe on the dashboard, then click Start.
      Making a version the standard
      Restart the server with unimatrix serve --default-recipe your-recipe-id. This is an explicit operator choice. This sets the initial selection. The main Start button always runs the currently selected recipe.
      Form changed / stale draft
      Exports refer to the last built draft. Testing and adding recipes are disabled after form changes until you build again, so you cannot accidentally test or publish settings different from the visible form.
      

      

      5. Suggested workflows
        

      1. Quick engine check: choose Compact v1, one development seed, level 1, one role and one replicate. Select Passive and Reciprocal, with no candidate models. Build → Preview → Start. This checks execution and scoring with no provider calls when peers are scripted.
        2. 

      2. Calibration: expand to all relevant domains, levels 1–3, both roles and at least four development seeds. Select six baselines and several models; enable No communication and No memory. Compare normal scores, paired effects and metric health. More coverage multiplies workload, so inspect the preview first.
        3. 

      3. Robustness: retain the same recipe and candidate settings, enable Reverse peer order and Rename agents. Test whether arbitrary presentation changes have large effects.
        4. 

      4. Revise and confirm: use development findings to adjust cases or weights, build a new version ID and repeat. Once choices are fixed, run Holdout. If you tune after inspecting it, reserve a fresh holdout set. Add the final recipe to benchmarks explicitly.
        5. 

      Combining more seeds, roles, levels, replicates, models and interventions multiplies run length. Start small to verify the mechanism, then increase coverage. No single diagnostic establishes that a recipe measures general intelligence.
