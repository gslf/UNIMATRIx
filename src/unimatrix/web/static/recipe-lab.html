            RECIPE LAB GUIDE
            How to develop a benchmark recipe
            

            Build recipe JSON files and evaluate them with the simulation engine.
            

            0. Quick start
            A template fixes domains, seeds, roles, replicates and holdout seeds; a society fixes the peers; the complexity preset fixes the layers. Fill the form writes these into the builder so you can adjust them. Build + smoke also saves the draft and starts a smoke evaluation with every scripted baseline, including the random floor and the oracle reference, to compare their scores.
            

            1. Every recipe-building option

            

            Saved drafts / Load draft
            Restore a saved draft and its form settings. Build again to save a new draft; edits do not change the loaded version.
            

            Start from
            Copies a named recipe's fixed peers, weights and supported budgets. Roles, replicates and seed lists are filled from its cases; the copied seeds may already have been used in evaluations. Change the seed lists for a new research design. Selecting another base replaces the form's previous settings.
            

            Recipe ID
            The machine-readable version identifier, using lowercase letters, digits, underscores or hyphens, up to 70 characters. Use a new ID such as social-benchmark-v2 when changing an existing recipe. The holdout ID adds -holdout.
            

            Recipe name and Description
            Name shown in selectors and description of the conditions being tested. Both are saved in the recipe.
            

            Domains D1–D8
            D1: information and prediction; D2: trade and negotiation; D3: cooperative construction; D4: shared resources; D5: relationships and commitments; D6: delegation and allocation; D7: knowledge transfer; D8: adaptation and recovery. Select a subset for a focused pilot or all eight for broad coverage. The overall score averages only the selected domains.
            


            Complexity
            Named layer presets: lenient (transparent commons, announced shock, no competitor), standard (the default rules) and harsh (drift, droughts, hidden quality, out-groups, rotation). Each selected preset adds one stratum per domain. Custom layers override individual knobs in each domain.
            

            Starting roles
            Scenario-defined advantaged or disadvantaged positions for the candidate. Select both to compare starting positions.
            

            Development seeds
            Integers controlling reproducible scenario instances. Enter 100-103, 110 for five seeds. Ranges include both ends. Duplicates, malformed ranges and more than 4096 seeds are rejected. Choose seed count from the preregistered effect and power calculation. Four seeds are a smoke screen.
            

            Holdout seeds
            Optional seeds, separate from development, for testing the fixed design on new instances. Tuning after inspecting holdout results requires fresh holdout seeds.
            

            Replicates per case
            One to four parallel worlds of each domain/seed/role combination: the same instance with its own noise (signal errors, demand, slips, chance events) and its own order of simultaneous actions. An explicit candidate inference seed is offset by the replicate number too. Replicates are not substitutes for different scenario seeds.
            

            Population by roles
            7–127 peers, grouped in roles of identical agents; Duplicate role copies one. A role is a scripted policy, whose goals are its dispositions (restraint, conditionality, norm compliance, demand…), or a saved model with a persona, objectives and a private briefing sent as its system message. Resources scales the role's starting inventory (not market or budget allotments). Holds the scenario's private information gives the role the first structural positions (best signal, counterparty, co-owner, learner), every access code, the market quality, the commons stock and convention examples. Roles are frozen in the recipe and held fixed across competitors. Large societies receive a rotating view of peers within the observation budget.
            

            Information and relations
            Generate one case to inspect positions, knowledge, resources, interests, contacts, dependencies and events. Choose a complete, ring, clustered or candidate-hub communication network. Check feasibility runs the witness without saving the case.
            

            Ranges
            Under Custom layers, a numeric knob with a "to" value is a range. Build draws one value per domain and seed, identical across roles and replicates, writes it into the cases and scores the family as one stratum under its label. The recipe stays explicit.
            

            Events and conditions
            Rules that fire once: at a tick, by chance within a window (different in every replicate) or when a gauge such as the commons stock, the service level or the completed tasks crosses a threshold. Effects: turnover of the structural partner or a random peer, a resource or stock shock, a change of a live rule (optionally for some ticks), a task fault, a further convention change. Built-in shocks and turnovers already move by ± the timing jitter around the midpoint of the selected recipe.
            

            Metric weights
            Three metrics per domain, with positive weights summing to 1. For example, 0.5, 0.25, 0.25 gives the first metric half the episode score. Metric definitions are fixed. Changed weights require a new recipe version and holdout evaluation.
            

            Build draft
            Validates the design and writes development and optional holdout JSON files in research storage. It makes no inference calls. The number of development episodes is domains × development seeds × roles × replicates. Each episode has one Protagonist plus the selected peers and uses the horizon of its base recipe (72 ticks for bundled recipes).
            

            Fixed budgets and draft checks
            Generation is limited by each model’s configured context (prompt + reasoning + answer), with no separate reasoning budget. The engine uses 24,000 observation bytes, 6,144 response-envelope bytes and at most 3 attempts. These limits and the bootstrap seed/resample count are inherited from the base recipe and visible in Generated recipe JSON; they are not editable in this page. Notes highlight missing roles, domains, too few seeds or missing holdout. They are advice, not a certification. Evaluation execution also checks scenario feasibility.
            

            

            What each metric weight controls
            

            All metrics below are normalized to 0–1 by the engine before weighting. Findings display them as 0–100. The weight changes a metric's contribution, not its definition or denominator.
            

            MetricWhat is measured
            

            D1.predictionForecast accuracy over 18 probes using a Brier-based score; missing forecasts score zero.
            

            D1.decisionFraction of correct route decisions over 12 windows.
            

            D1.updateFraction of correct decisions in the six windows requiring an update.
            

            D2.private_gainCandidate utility normalized against the scenario's fixed utility bounds, across six markets.
            

            D2.joint_gainJoint trading surplus relative to the fixed attainable surplus, across six markets.
            

            D2.deliveryDelivered quantity relative to the required quantity, across six markets.
            

            D3.completionFraction of four verified service milestones completed.

            D3.efficiencyCompleted milestones per 1 + total contribution cost, relative to a preregistered efficiency bound.
            

            D4.serviceMean service delivered relative to target over the episode.
            

            D4.continuityThe lowest mean service in the four closing windows at the end.
            

            D4.reserveFinal common stock relative to the reserve target of the complexity layer.
            

            D5.relational_utilityNormalized candidate utility across 12 relationship opportunities and disputes.
            

            D5.commitment_resolutionResolution credit assigned by the scenario across those 12 opportunities.

            D8.convention_transferFraction of the interactions verified after the shock, one per convention window, that use the right convention.
            

            

            Scripted policy catalog
            

            All nine choices are available as fixed peers. The first six are also available as candidate baselines. These policies share task-specific rules; their names do not imply distinct behavior in every domain. As peers they react to the candidate: those who honour norms keep an agreed commons quota, follow the coordinator's work assignments, try suggested conventions and co-sign the release of a bad deal. They never start a norm themselves.
            

            

            Passive
            Returns an empty decision. Useful for establishing what the environment and peers accomplish without candidate action.
            

            Random
            Deterministically samples zero to two observable actions and emits uniform forecasts. Useful as a weak reference.
            

            Independent
            Uses task rules but avoids trading, knowledge transmission and construction requiring complementary cooperation; on the commons it matches others only while they are careless and honours norms half of the time.
            

            Greedy
            Demands a higher trading gain, sets a higher asking price, rejects costly relationship commitments and free-rides on the commons, ignoring quotas and assignments.
            

            Reciprocal
            Inspects market quality, tracks relationship outcomes, rejects costly commitments and uses dispute repair rules.
            

            Coordinator
            Uses task coordination and dispute repair rules. As the candidate it leads: it proposes the commons quota, assigns construction work and shares conventions that work.
            

            Prudent
            Inspects market quality and uses relationship history to avoid costly commitments and previously unreliable partners.
            

            Opportunist
            Uses higher asking prices, may withhold committed relationship work when incentives favor it, never co-signs a release and free-rides on the commons.
            

            Information
            Uses the shared task rules with market-quality inspection. Useful when varying the information available through peers.
            

            

            2. Every evaluation option and how to combine them

            

            Evaluation name
            A label for this experiment in history, for example v2 · three-model calibration. Multiple evaluations may test the same draft.
            

            Mode
            Smoke runs one case per domain and complexity, mostly to check that a recipe executes and separates scripted baselines. Pilot runs candidate models seed block by seed block, paired against a reference baseline on identical seeds, and stops as soon as the paired difference is settled (clearly above the minimum effect, clearly not, or precise enough). Full runs every case.
            

            Cases to test
            Development runs the development recipe; Holdout runs its separate seed set. Holdout is rejected if the draft has none. The selected split is recorded with the findings.
            

            Scripted baselines
            Passive makes no actions; Random samples available actions (the floor); Independent avoids some cooperation; Greedy applies self-interested rules; Reciprocal uses interaction history and repair rules; Coordinator includes coordination and repair; Oracle decides from the full world state (a strong reference, research only). They are limited programmed policies, not complete personalities. Select any subset. With only scripted peers they make zero provider calls and run in worker processes.
            

            Candidate models
            Select up to eight saved candidate configurations from the benchmark page. Each gets a normal study plus one study per selected intervention. The preview copies the configurations; changing a model file afterwards does not alter that preview or an active evaluation. Equivalent model files cannot be selected twice.
            

            No communication
            For the candidate only, hide incoming messages and other agents' shared artifacts, and suppress outgoing messages and explicit publishing/teaching/access-sharing operations. Message records are also removed from recent events and retrieval. Other agents can still communicate, and the candidate still observes material effects. This tests dependence on the blocked channels, not every possible social signal.
            

            No memory
            Hide the candidate's private note, retrieved memory and recent event history; suppress updates to its private note and retrieval query. Current world state, receipts and current inbox remain available. This is an external-memory intervention, not deletion of a model's training or any provider-side state.
            

            Reverse peer order
            Reverse the peer list in the candidate's observation while preserving its contents. Large changes may indicate sensitivity to presentation order.
            

            Rename agents
            Replace peer identifiers consistently in the candidate's observation and map returned identifiers back. It probes dependence on arbitrary labels. Compare the change with uncertainty; a change alone does not prove a flaw.
            

            Combining interventions
            Each checked intervention produces a separate variant against the normal model. Checking No memory and No communication creates three studies per model, not a single variant with both disabled. Scripted baselines run normally; their intervention boxes are ignored when no candidate models are selected.
            

            Preview evaluation
            Freezes the selected draft, model configurations, baselines and interventions without calling providers. Shows study count, total episodes, maximum provider decisions, maximum attempts and output-token bound. Baseline decisions are not provider calls. Fixed reference models are included in the provider count. Input tokens and currency costs are not estimated here. A evaluation is limited to 20,000 episodes; reduce cases, models or variants if it exceeds this limit.
            

            Start evaluation
            Run the frozen preview, including configured provider calls. After edits, rebuild or preview again. Only one benchmark or research evaluation runs at a time. Research results do not enter leaderboards.
            

            Pause / Resume
            Pause preserves completed work and recorded decisions, including partial episodes. Resume continues with the saved recipe and model configuration. The original engine and research implementation are required. Finished experiments, including ones with failed studies, are repeated by creating a new evaluation.
            

            Evaluation history / Refresh
            Load saved evaluations, including interrupted runs after a restart. Running evaluations refresh automatically. Failed studies retain their errors and are excluded from scored findings.
            

            

            Example: seven baselines + two models + two interventions = 7 + 2 × 3 = 13 studies. An eight-episode recipe therefore runs 104 episodes. With scripted peers, only the six model studies make provider calls: at most 11,520 primary decisions, or 34,560 attempts including retries. Scripted studies run in worker processes.
            

            

            3. How to read every finding

            

            Study status and Episodes
            Pending, running, paused, completed or failed. A score requires every episode in that study to finish. A failed study keeps its error message; missing results are never treated as zero. The evaluation can finish with failures while retaining other complete studies.
            

            Score and 95% interval
            A 0–100 score using the draft's metric weights, equal weighting of cases within each domain and equal weighting of domains. The bootstrap resamples scenario seeds. With one seed, an interval may collapse to a point; that is not proof of certainty.
            

            Invalid decisions
            Separate counts for the candidate and for all agents, including configured peers. Candidate counts cover resolved decisions; saved requests waiting for an interrupted barrier are not resolved decisions. Infrastructure errors and rejected typed operations are recorded separately. These are counts, not rates. Historical records without candidate counters display a dash.
            

            Completed studies
            Complete studies included in the findings divided by all planned studies. Partial studies contribute no scores or metric health values.
            

            Model score spread
            Highest minus lowest score among completed normal candidate studies; requires two models and excludes baselines and interventions.
            

            Paired intervention difference
            Normal score minus variant score for the same model and exact cases. Positive means performance fell under the intervention; negative means it improved. A confidence interval spanning zero is inconclusive in this sample. Communication/memory dependence and sensitivity to renaming/order have different interpretations.
            

            Metric health: Mean and Range
            Average, minimum and maximum normalized metric scores (0–100), pooled over complete normal models and baselines. Each observation is one system/episode result. Intervention variants are excluded.
            

            Near maximum / Near zero
            Fractions of observations at or above 98%, or at or below 2%. A fraction of 80% triggers a note. Frequent maxima suggest a ceiling; frequent zeroes may reflect excessive difficulty, ineffective policies or invalid model output. Baselines are included, so check which systems produced the pattern.
            

            Debug metrics
            For every metric of the completed normal studies: the mean of each system, weak and strong references, spread and effective weight (the share of its domain's score differences it carries, weight × spread). Flags identify patterns: free points for trivial policies, inaction or noise that pays, saturated, dead or society-driven metrics, and scores that rise with the candidate's message or action volume. The examples open the explorer on the episode's Metrics tab, which lists the events behind each score.
            

            Recommendations
            Diagnostics suggest cells and effects to investigate. They do not change weights or approve a recipe.
            

            Export findings
            Downloads the selected evaluation's status, study summaries, diagnostics and exact tested recipe. An export during execution is explicitly partial; full results and replay evidence remain in local research storage. Intervention model-call records include the actual transformed input and the original model output before suppression or identifier remapping.
            

            

            4. Drafts, exports and adding a version to benchmarks

            Generated recipe JSON
            Read-only JSON for the built development recipe.
            Download development / holdout JSON
            Download either generated recipe for inspection or version control. Holdout is available only when you supplied holdout seeds.
            Create a benchmark recipe
            Open recipeManager, choose a saved draft and development or holdout, then select Create recipe. This page also manages deletion and shows catalog statistics. Existing recipes are never overwritten; build a new Recipe ID for a different version.
            Making a version the standard
            Restart the server with unimatrix serve --default-recipe your-recipe-id. This is an explicit operator choice. This sets the initial selection. The main Start button always runs the currently selected recipe.
            Form changed / stale draft
            Exports refer to the last built draft. Rebuild after edits to enable testing and saving.
            

            

            5. Decision probes
            Harvest takes observations from one completed study, preferring reciprocal/oracle. Each model receives the recorded input, including memory, in one independent call. Responses do not advance the simulation.
            Decision match compares complete operations at each position, including quantities and nested terms, plus forecast similarity. It takes the higher match to reciprocal or coordinator, both given the same observation. Empty reference ticks are excluded; invalid responses score zero on informative ticks. Literal message matches and the full-state oracle are separate diagnostics. Alternative effective strategies can still receive low matches.
            Correlation uses only completed normal full-mode studies in this evaluation with the same model configuration. At least three models and nonconstant ranks are required. Smoke and pilot are excluded. Replacing the bank makes previous screens stale.
            

            6. Suggested workflows
              

            1. Quick engine check: choose Standard v1, one development seed, one role and one replicate. Select Passive and Reciprocal, with no candidate models. Build → Preview → Start. This checks execution and scoring with no provider calls when peers are scripted.
              2. 

            2. Calibration: expand to all relevant domains, both roles and at least four development seeds. Select every baseline (random and oracle give the weak and strong references) and several models; enable No communication and No memory. Compare normal scores, paired effects and metric health. More coverage multiplies workload, so inspect the preview first.
              3. 

            3. Robustness: retain the same recipe and candidate settings, enable Reverse peer order and Rename agents. Test whether arbitrary presentation changes have large effects.
              4. 

            4. Revise and confirm: use development findings to adjust cases or weights, build a new version ID and repeat. Once choices are fixed, run Holdout. If you tune after inspecting it, reserve a fresh holdout set. Add the final recipe to benchmarks explicitly.
              5. 

            Combining more seeds, roles, replicates, models and interventions multiplies run length. Start small to verify the mechanism, then increase coverage. No single diagnostic establishes that a recipe measures general intelligence.
